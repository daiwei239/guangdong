# 当前五步流程实现总结

本文档用于说明当前系统“五步流程”中每一步的实现内容、实现方式和所采用的方法。这里的“五步”对应前端页面展示的五个阶段；需要注意的是，后端在线真实流程实际已经拆成六步，其中前端第 5 步把“候选子网搜索”和“匹配验证”合并在一起展示。

---

## 第一步：元数据采集

### 1. 这一步包含什么

当前这一步采集的不是单一指标，而是一套完整的异构资源元数据，主要分为以下几类：

- 资源类别信息：包括 `CPU`、`GPU`、`FPGA`、`MEMORY`、`STORAGE`、`NIC`、`SWITCH`
- 静态属性信息：描述资源本身的固有能力，例如 CPU 核数、GPU 显存、FP16/FP32 算力、存储吞吐、网卡带宽、交换机端口数等
- 动态状态信息：描述资源当前运行状态，例如利用率、空闲显存、队列长度、功耗、温度、丢包率、拥塞程度、是否可用等
- 语义标签信息：例如 `accelerator`、`parallel`、`network`、`fabric`、`high_bandwidth` 这类标签，用于表达资源的语义角色
- 拓扑上下文信息：包括 `cluster_id`、`host_id`，以及 `topo_context` 中的 `server_id`、`rack_id`、`zone_id`、`network_tier`、`hop_level`

从系统角度看，这一步的目标不是简单“拿到资源列表”，而是把后续做资源图构建、候选搜索、规则评分、图编码所需的基础描述全部准备好。

### 2. 当前是怎么实现的

当前实现不是接真实监控平台、资源编排平台或调度器接口，而是采用 mock 方式生成一份资源快照。

实现入口是 `resource_service.generate_snapshot()`。这一过程会做两件事：

- 先调用 `MockResourceGenerator.generate_resources()` 生成一批异构资源节点
- 再调用 `MockTopologyGenerator.generate_edges()` 基于这些资源节点补充资源之间的关系边

生成完成后，资源节点和边会被缓存在服务内存里，同时写入数据库，作为当前系统的资源快照。

### 3. 用的是什么方法

这一步本质上采用的是“基于规则模板的随机模拟生成”方法，而不是在线采集方法。

具体来说：

- 资源种类和数量由固定模板控制，例如 CPU、GPU、FPGA 等各生成若干个
- 每类资源的静态属性从预设候选值中随机抽样
- 动态状态通过随机范围采样生成，模拟不同负载和可用性
- 拓扑上下文通过 cluster、host、rack 等字段规则推导

这种方法的好处是：

- 可以稳定产出结构完整的测试数据
- 便于验证后续图构建、搜索、评分、编码流程
- 能在没有真实集群接入的情况下先把系统主链路跑通

### 4. 当前阶段的特点

所以，第一步当前更准确地说，不是“真实元数据采集”，而是“异构资源元数据模拟生成与标准化组织”。它已经能支撑后续步骤运行，但数据来源仍然是 mock，而不是真实生产环境。

## 第二步：资源图构建

### 1. 这一步包含什么

这一步的核心是把第一步采集到的资源元数据，从“离散资源列表”转成“统一资源图”。

图中的内容主要包括：

- 节点：即不同类别的资源实体，例如 CPU、GPU、MEMORY、NIC 等
- 边：即资源之间的关系

当前支持的边关系类型包括：

- `CONNECTED_TO`
- `SAME_HOST`
- `SAME_RACK`
- `SHARES_MEMORY`
- `COMPETES_BANDWIDTH`
- `LOW_LATENCY_LINK`
- `SCHEDULING_DEPENDENCY`

因此，这一步构建出来的不是普通同构图，而是带有多种节点类型和多种关系语义的异构资源图。

### 2. 当前是怎么实现的

当前实现入口是 `graph_service.build_networkx_graph(resources, edges)`。

整体过程是：

1. 接收第一步生成的资源节点和关系边
2. 调用 `GraphBuilder.build_graph()` 把资源节点加入图中
3. 把资源之间的关系边也加入图中
4. 得到一张内存中的 `NetworkX` 图对象

除此之外，系统还做了两类配套处理：

- 使用 `GraphBuilder.to_frontend_snapshot()` 把图转换成前端大屏可视化需要的数据结构
- 使用 `sync_to_neo4j()` 把图同步到 `Neo4j`，作为图数据库侧的可选副本

### 3. 用的是什么技术

这一步的核心技术是 `NetworkX`。

选择 `NetworkX` 的原因很直接：

- 适合当前阶段在内存中快速构建图结构
- 便于后续做子图搜索、连通性判断、邻域扩展、子图截取等操作
- 对规则搜索和评分逻辑友好

同时，系统又引入了 `Neo4j` 作为可选同步目标，但当前主链路并不依赖 Neo4j 做计算，真正在线使用的主要还是 `NetworkX` 图。

所以如果一句话概括第二步：当前是用 `NetworkX` 在内存中构建异构资源图，并可选同步到 `Neo4j`。

### 4. 当前阶段的特点

这一阶段已经不是占位逻辑，而是完整可运行的资源图构建实现。它的定位是为后续候选搜索和图编码提供统一图表示，因此更偏“在线计算图”，而不是“数据库主导图”。

## 第三步：任务需求表达

### 1. 这一步包含什么

这一步的目标是把任务从“一个抽象调度请求”表达成结构化的任务画像，供搜索、评分和编码模块使用。

当前任务画像包含的主要内容有：

- 任务类型：如计算密集型、数据密集型、通信密集型、混合型
- DAG 节点信息：表示任务阶段结构
- 计算需求：例如 CPU 核数、GPU 数量、FP16 算力需求
- 内存需求：例如容量需求
- 存储需求：例如容量和吞吐需求
- 网络需求：例如带宽和时延要求
- 能耗限制：`energy_limit`
- QoS 时限：`qos_deadline_sec`
- 优先级：`priority`
- 约束条件：例如最小 GPU 显存、最小网络带宽、最大网络时延、是否偏好同机架、是否偏好低时延

从功能上说，这一步是在构造任务的“需求向量”和“硬/软约束集合”。

### 2. 当前是怎么实现的

当前实现入口是 `task_service.generate_task()`。

内部会调用 `MockTaskGenerator.generate_task_profile()`，随机生成一个任务画像，并将其组织为统一的 `TaskProfile` 结构。生成后任务既会缓存到服务中，也会持久化到数据库，便于后续查询和复用。

换句话说，当前系统不是从真实提交任务、工作流描述文件、调度请求或运行时 profile 中提取任务需求，而是先用 mock 方式生成标准任务画像。

### 3. 用的是什么方法

这一步采用的方法可以概括为“模板驱动的任务画像生成 + 结构化约束表达”。

具体来说：

- 先按任务类型准备不同的典型任务模式
- 再根据任务类型生成 DAG stage 结构
- 然后生成与该类型匹配的计算、存储、网络等需求字段
- 最后附加 QoS、能耗和拓扑偏好约束

这样做的价值在于，后续模块面对的不是一段自然语言描述，而是一份统一 schema 的任务对象。无论是规则筛选、规则评分，还是后面的图神经网络编码，都可以直接消费这一结构。

### 4. 当前阶段的特点

因此第三步当前不是“真实任务需求解析”，而是“统一任务画像模拟生成”。它已经把任务侧输入规范化了，但来源仍然是 mock，而不是业务系统真实输入。

## 第四步：图表示学习

### 1. 这一步包含什么

这一步的目标是把前面构建好的异构资源图，从符号化结构进一步变成可计算的向量表示。

当前这一步主要包含三层内容：

- 节点特征构建：把 CPU、GPU、NIC、STORAGE 等不同资源的原始属性转成数值特征
- 图消息传递编码：让图中的邻接关系、关系类型、边属性参与表示学习
- 子图或整图嵌入生成：输出统一维度的表示向量 `z_subgraph`

最终产物包括：

- 各类型节点的 embedding
- 不同候选子图的 embedding
- 全图 embedding

### 2. 当前是怎么实现的

这一阶段已经是真实执行逻辑，不再是占位步骤。

实现入口是 `matching_service.encode_resource_graph(resources, edges, task.task_type)`，候选子图则通过 `encode_candidate_subgraph(...)` 单独编码。

具体流程是：

1. 先通过 `build_mock_heterodata_from_resources(...)` 把资源图转换成异构图数据结构
2. 使用 `ResourceFeatureBuilder` 为不同类型资源构造原始特征向量
3. 使用 `ResourceFeatureEncoder` 把不同类型输入映射到统一隐藏维度
4. 使用 `ResourceGraphEncoder` 做异构图编码
5. 根据任务类型对不同资源类型的表示做加权 pooling
6. 得到最终的 `z_subgraph`

### 3. 用的是什么技术和方法

这一步核心采用的是异构图神经网络方法。

具体技术上包括：

- `PyTorch`
- `PyTorch Geometric`
- `HeteroConv`
- relation-specific `GATConv`

方法上可以概括为：

- 先做“类型专属特征编码”，因为 CPU、GPU、NIC 这些资源的原始属性维度和语义不同，不能直接拼接
- 再做“关系感知消息传递”，不同边类型分别建模，而不是把所有边压成一种关系
- 最后做“任务感知池化”，不同任务类型对资源类型关注重点不同，因此 pooling 权重不是完全一样

另外，边属性目前也参与编码，统一整理为 5 维属性，例如带宽、时延得分、拥塞得分、可靠性、权重。

### 4. 当前阶段的特点

这一阶段最关键的现状是：图编码器已经真实接入在线流程，但它目前更多是作为内部表示工件存在，还没有直接主导最终排序结果。也就是说，第四步已经是真实 GNN 编码，但第五步最终决策仍以规则法为主。

## 第五步：候选子网搜索与匹配验证

### 1. 这一步包含什么

前端页面把这一步展示为一个阶段，但实际上它在后端里包含两个子过程：

- 候选资源子网搜索
- 候选结果评分、排序与 Top-1 验证

输出内容主要包括：

- Top-N 候选子图
- 每个候选子图的评分结果
- Top-1 最优子图
- 对 Top-1 的验证结论与调度建议

### 2. 当前是怎么实现的

当前实现入口在 `matching_service.match_task(...)`。

内部执行逻辑大致是：

1. 调用 `BeamSearchSubgraphFinder.search(...)` 搜索候选子图
2. 对每个候选子图再调用 `encode_candidate_subgraph(...)` 生成子图向量
3. 使用 `scoring_service.score_candidate(...)` 对候选子图逐个评分
4. 按 `final_score` 排序，得到 Top-1
5. 调用 `validate_top1(...)` 对 Top-1 做容量、性能、拓扑、QoS 等约束校验

因此它不是单纯搜索，也不是单纯评分，而是“搜索 + 评分 + 排序 + 验证”的组合阶段。

### 3. 用的是什么方法

这一步目前主要采用的是规则方法，不是端到端 learned ranking。

前半段搜索方法是：

- `RuleFilter` 先做资源粗筛
- 根据任务类型和资源状态做 seed 打分
- 用 `Beam Search` 做邻域扩展
- 用连通性检查和最小规模补足策略形成候选子图

所以搜索方法可以概括成“规则粗筛 + Beam Search 子图搜索”。

后半段评分验证方法是：

- 计算 `capacity_score`
- 计算 `performance_score`
- 计算 `topology_score`
- 计算 `qos_score`
- 计算通信、能耗、负载等 `cost`
- 最终按加权公式合成 `final_score`

最后再对 Top-1 做显式阈值验证，看容量、性能、拓扑、QoS 是否满足要求。

### 4. 当前阶段的特点

这一阶段的最大特点是：虽然第四步已经引入了图神经网络编码器，但第五步最终主链路仍然是规则搜索和规则评分。

也就是说，当前系统的实际状态可以总结为：

- 搜索靠规则筛选和 Beam Search
- 决策靠规则评分和阈值验证
- 图编码结果已经接入，但暂时更多作为内部表示能力，而不是最终排序主导信号

因此，如果从工程成熟度来讲，第五步已经具备“可运行、可解释、可验证”的优点，但还没有进入“学习排序主导决策”的阶段。

---

## 总结

当前五步流程的整体特点可以概括为：

- 第一步和第三步的数据来源仍然是 mock 生成
- 第二步的资源图构建已经是真实可运行的 `NetworkX` 图构建
- 第四步的异构图表示学习已经真实接入在线流程
- 第五步的主决策逻辑仍然以规则搜索和规则评分为主

所以整个系统目前属于一种“前端展示五步、后端真实链路已跑通、GNN 已接入但规则仍主导”的阶段性实现形态。这种形态的优点是链路完整、可解释、便于迭代；后续如果继续升级，重点就会放在让编码器输出真正参与 rerank 和最终决策。
